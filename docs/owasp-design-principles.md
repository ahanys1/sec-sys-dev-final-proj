### 1. Minimize Attack Surface Area

The principle of minimizing attack surface area focuses on reducing the number of potential entry points and exposed components that an attacker could exploit. For our incident-reporting application, this principle is addressed by limiting exposed routes, services, and framework features within the Next.js monolith. Authentication and server-side role-based authorization protect application functionality, restricting incident submission, review, and administrative operations to authenticated users with appropriate permissions. Database operations are performed server-side using Prisma rather than exposing direct database access to clients. The application also avoids unnecessary deletion endpoints by using account deactivation, incident closure, and append-only audit records. The production deployment further reduces exposure through restricted network services and the use of Caddy as a reverse proxy.

**Related Security Requirements:** SR-1 (Authentication), SR-4 (Role-Based Access Control), SR-5 (Server-Side Authorization).

**Verification:** Database-backed integration tests and manual browser testing verified that unauthenticated and unauthorized users are denied access to tested protected functionality. Direct navigation to restricted administrative pages returned generic 404 responses for unauthorized roles. Deployment configuration and network exposure verification are documented in `docs/deployment.md`.

**Supporting Evidence:** `src/lib/auth/guard.ts`, `src/lib/auth/page.ts`, `tests/db/incidents.test.ts`, `tests/db/admin-settings.test.ts`, `tests/db/admin-audit.test.ts`, `docs/threat-model.md`, `docs/deployment.md`; PRs #53, #54, #57, and #60.

### 2. Establish Secure Defaults

The principle of establishing secure defaults ensures that the application operates with restrictive security settings unless explicitly authorized otherwise. For our incident-reporting application, this principle is addressed by requiring authentication for protected functionality and denying access when valid permissions cannot be established. Accounts are created by Administrators, with role assignments restricted to authorized administrative operations. Server-side authorization prevents users from modifying their own roles or performing operations outside their assigned permissions. Session cookies use security attributes including HttpOnly, Secure, and SameSite=Strict in accordance with the session design. Incident status changes and classification are restricted to Reviewers, while administrative privileges do not automatically grant unrestricted access to reviewer-specific operations. These defaults ensure that security protections are enabled without requiring users to configure them manually.

**Related Security Requirements:** SR-1 (Authentication), SR-3 (Secure Session Management), SR-4 (Role-Based Access Control), SR-5 (Server-Side Authorization), SR-6 (Role Modification Restrictions).

**Verification:** Authentication and session tests provide evidence of secure session handling, while account-management tests verify restrictions on self-role modification. Database-backed integration tests and manual authorization testing confirmed that unauthenticated requests and unauthorized cross-role operations are rejected within the tested workflows. Direct API authorization checks supplement role-appropriate navigation, ensuring that access restrictions do not depend solely on interface visibility.

**Supporting Evidence:** `src/lib/auth/session.ts`, `src/lib/auth/guard.ts`, `src/lib/auth/page.ts`, `src/lib/admin/users.ts`, `tests/auth/session-helpers.test.ts`, `tests/db/auth.test.ts`, `tests/db/admin-users.test.ts`, `tests/db/incidents.test.ts`, `tests/db/admin-settings.test.ts`; PRs #38, #51, #53, and #54.

### 3. Principle of Least Privilege (POLP)

The principle of least privilege ensures that users and system components receive only the permissions necessary to perform their intended functions. For our incident-reporting application, this principle is addressed through role-based access control (RBAC), with explicitly defined permissions for Users, Reviewers, and Administrators. Each role is restricted to its assigned responsibilities through server-side authorization rather than relying on frontend controls. All users, including Administrators, are prohibited from modifying their own roles to prevent unauthorized privilege escalation. Additionally, database access is restricted through separate application and database owner roles. The application database role operates without superuser or schema-management privileges and is granted only the permissions necessary for application functionality. Access to the audit table is further restricted to SELECT and INSERT operations, reducing the potential impact of compromised application credentials or components.

**Related Security Requirements:** SR-4 (Role-Based Access Control), SR-5 (Server-Side Authorization), SR-6 (Role Modification Restrictions).

**Verification:** Database-backed integration tests and manual authorization testing verified permitted and prohibited operations across application roles within the tested workflows. Manual PostgreSQL testing confirmed that the application database role lacks superuser privileges, permits SELECT and INSERT operations on the audit table, and rejects UPDATE and DELETE attempts. The absence of TRUNCATE privileges was also confirmed. These results provide evidence of least privilege enforcement at both the application and database levels.

**Supporting Evidence:** `src/lib/auth/guard.ts`, `src/lib/auth/page.ts`, `src/lib/admin/users.ts`, `tests/db/admin-users.test.ts`, `tests/db/incidents.test.ts`, `tests/db/admin-settings.test.ts`, `tests/db/schema.test.ts`, `docs/threat-model.md`, `docs/sdl.md`; PRs #51, #53, and #54.

### 4. The Principle of Defense in Depth

The principle of defense in depth emphasizes using multiple layers of security controls so that the failure or compromise of one mechanism does not necessarily compromise the entire system. For our incident-reporting application, this principle is addressed through a combination of authentication, secure session management, role-based access control (RBAC), server-side input validation, and parameterized database operations. Authentication establishes user identity, while server-side authorization independently verifies permissions for protected operations. Strict input validation using Zod, Prisma database operations, and restricted database privileges provide additional protection against malicious input and unauthorized data manipulation. Browser security headers and React's default escaped rendering provide further protection against client-side threats.

Audit logging incorporates multiple protective layers through application-level restrictions, append-only database permissions, and database triggers that reject audit record modification. Transactional audit logging also ensures that audited business operations are rolled back when their associated audit insertion fails. Secure error handling and application logging support the detection and investigation of security-related events without unnecessarily exposing internal implementation details. Together, these controls reduce reliance on any single security mechanism.

**Related Security Requirements:** SR-1–SR-8 (Authentication, Password and Session Protection, Authorization, Input Validation, and Parameterized Queries), SR-9–SR-11 (Logging Protections), SR-12–SR-13 (Error Handling).

**Verification:** Database-backed integration tests and manual security testing verified multiple layers of protection, including rejected unauthorized requests, invalid input handling, safe rendering of stored XSS payloads, and audit record protection. Manual PostgreSQL testing confirmed that restricted database permissions and audit rejection triggers independently protect audit records against modification. Transactional integration tests verified that business operations are rolled back when audit insertion fails. Targeted sensitive-data testing confirmed that the tested incident description was absent from application logs and audit records. Targeted SQL injection testing demonstrated no unauthorized query behavior within the tested workflows. Additional local Slice 7 verification included SAST, authenticated DAST, malformed-input testing, sensitive-data leakage checks, and database-level audit protection following backup restoration. These results provide supporting evidence for the implemented defense-in-depth controls within the documented verification scope.

### 5. Fail Securely

The principle of failing securely ensures that application errors and unexpected conditions do not result in weakened security controls or unauthorized access. For our incident-reporting application, this principle is addressed by denying operations when authentication or authorization checks fail, rejecting invalid input, and handling database or application errors without exposing sensitive information. Error responses provide appropriate feedback to users while preventing the disclosure of internal system details, such as database queries, credentials, or stack traces. Incident creation, status changes, classification, comment creation, and administrative settings and category updates incorporate transactional audit logging to preserve data integrity and mandatory auditing when failures occur. Concurrent incident status updates are controlled through conditional database updates to prevent conflicting or invalid state transitions. Detailed server-side logging is designed to exclude passwords, tokens, and full incident descriptions (SR-9). These measures help the application recover from errors without compromising its security requirements.

**Related Security Requirements:** SR-5 (Server-Side Authorization), SR-7 (Input Validation), SR-9–SR-11 (Audit Logging), SR-12 (No Queries in Error Messages), SR-13 (Detailed Server-Side Error Logging). Supporting requirements: FR-11–FR-12 (Required, Append-Only Audit Trail), NFR-2, NFR-5, NFR-6 (Safe Errors, Concurrent Data Integrity, and Graceful Recovery).

**Verification:** Database-backed integration tests and manual security testing verified the rejection of unauthorized requests, malformed input, invalid status transitions, and conflicting incident updates. Manual browser testing confirmed that unauthorized page access and duplicate category submissions returned appropriate error messages without exposing internal implementation details. Transactional audit integration tests confirmed that a business operation is rolled back when its associated audit insertion fails. Additional settings tests confirmed rollback following a simulated transaction failure. Targeted testing verified that the tested incident description was excluded from application logs and audit records. Comprehensive dependency failure, sensitive-data leakage, and recovery testing remain subject to final security verification.

**Supporting Evidence:** `src/lib/audit.ts`, `src/lib/auth/guard.ts`, `src/lib/http.ts`, `tests/db/audit.test.ts`, `tests/db/incidents.test.ts`, `tests/db/admin-settings.test.ts`, `docs/sdl.md`; PRs #53, #54, and #59.

### 6. Don't Trust Services

The principle of not trusting services emphasizes that external and internal services should not be assumed secure simply because they are part of the application's architecture. For our incident-reporting application, this principle is addressed by treating interactions between the Next.js application, PostgreSQL database, and third-party dependencies as trust boundaries. Third-party dependencies and AI-generated code are treated as supply-chain inputs requiring review rather than being assumed trustworthy. Client-submitted data is validated server-side, while database operations use parameterized queries and restricted credentials to reduce the risk of injection and unauthorized data access. The application also validates security-sensitive values, such as user roles, rather than blindly accepting unexpected data. Third-party dependencies are subject to automated vulnerability scanning, dependency monitoring, and security review.

SR-14 prohibits unencrypted storage of database credentials. The application addresses this requirement through dotenvx-encrypted environment configuration, with the decryption key stored separately in AWS Secrets Manager for the live deployment. The EC2 instance retrieves the key at runtime through a restricted IAM role authorized to access the required secret. Deployment scripts reject unencrypted configuration files, enforce strict decryption, and verify that the decryption key is not retained in container environments. Database owner and application credentials are separated to restrict the privileges available to the running application. These controls address the credential-storage concerns identified in threat-model decision D-4 and reduce reliance on implicit trust between application components.

**Verification:** Database-backed integration tests verified the rejection of malformed input, unauthorized operations, and attempted role modifications. Manual PostgreSQL testing confirmed that the application database role operates with restricted privileges. Transactional audit tests demonstrated that failed audit insertion prevents associated business changes from persisting. Automated dependency and secret-scanning controls are incorporated into the project's CI workflow. Live deployment verification confirmed successful startup using AWS Secrets Manager, the absence of the decryption key from container environments and application image history, and the absence of `.env.keys` from the checked deployment host directories. External connectivity testing confirmed that the PostgreSQL port was not externally accessible from the tested networks. Broader dependency failure testing remains subject to final security verification.

**Supporting Evidence:** `src/lib/request.ts`, `src/lib/auth/guard.ts`, `tests/db/schema.test.ts`, `tests/db/audit.test.ts`, `tests/db/admin-users.test.ts`, `tests/db/incidents.test.ts`, `scripts/live-up.sh`, `scripts/live-run.sh`, `scripts/aws-provision.sh`, `Makefile`, `docs/threat-model.md`, `docs/deployment.md`, `docs/sdl.md`, `.github/dependabot.yml`; PRs #51, #53, #54, #57, #59, and #60.

### 7. Separation of Duties

The principle of separation of duties emphasizes dividing sensitive responsibilities among different roles to reduce the risk of unauthorized actions, misuse of privileges, and conflicts of interest. For our incident-reporting application, this principle is addressed through the separation of responsibilities among Users, Reviewers, and Administrators. Users are responsible for submitting incidents and viewing their own incident summaries, Reviewers are responsible for managing incident reviews, classification, and status updates, and Administrators are responsible for managing user accounts, role assignments, incident categories, and system configuration. Administrators can also view all incidents and add comments, as required by FR-9 and FR-10.

Incident status changes and classification are reserved exclusively for Reviewers; Administrators do not operate as an unrestricted super-role. These responsibilities are enforced through server-side role-based authorization to prevent users from performing operations outside their assigned roles. All users, including Administrators, are prohibited from modifying their own roles. This implementation supports role-based separation of responsibilities but does not establish independent approval or prevent self-review through multiple accounts held by one person; those capabilities would require additional explicit controls. No application role is permitted to alter audit history, although protection against privileged database operators requires separate consideration.

**Related Security Requirements:** SR-4 (Role-Based Access Control), SR-5 (Server-Side Authorization), SR-6 (Role Modification Restrictions).

**Verification:** Database-backed integration tests and manual browser testing verified permitted and restricted operations across the three application roles. Testing confirmed that Users and Reviewers cannot perform administrative operations, Administrators cannot modify their own roles, and incident status changes and classification are restricted to Reviewers. Administrators retain permitted access to all incidents and can add comments to closed incidents. Manual PostgreSQL testing confirmed that the application database role cannot modify or delete existing audit records. Live deployment testing further demonstrated role-based access restrictions through both browser navigation and direct API requests. Supporting requirements: FR-9–FR-12 and SR-11.

**Supporting Evidence:** `src/lib/auth/guard.ts`, `src/lib/auth/page.ts`, `src/lib/admin/users.ts`, `tests/db/admin-users.test.ts`, `tests/db/incidents.test.ts`, `tests/db/admin-settings.test.ts`, `tests/db/schema.test.ts`, `docs/design.md`, `docs/threat-model.md`, `docs/deployment.md`, `docs/sdl.md`; PRs #51, #53, #54, #59, and #60.

### 8. Avoid Security by Obscurity

The principle of avoiding security by obscurity emphasizes that application security should not depend on hiding implementation details, endpoints, or system functionality from potential attackers. For our incident-reporting application, this principle is addressed through explicit authentication, server-side authorization, and input validation rather than relying on concealed administrative pages or hidden interface elements. Administrative and reviewer functionality requires appropriate role permissions regardless of whether the corresponding routes or controls are visible in the user interface. Role-specific navigation improves usability but does not serve as an authorization mechanism.

Sensitive credentials and configuration values are protected through encrypted storage and controlled access rather than relying on undisclosed file locations or naming conventions. The application uses dotenvx-encrypted environment configuration, with the decryption key stored separately in AWS Secrets Manager for the live deployment. Access to the key is restricted through IAM permissions, addressing the credential-storage concerns identified in threat-model decision D-4. These measures allow application security controls to remain effective even when an attacker understands the system's structure, implementation, and endpoint locations.

**Related Security Requirements:** SR-1 (Authentication), SR-4 (Role-Based Access Control), SR-5 (Server-Side Authorization), SR-14 (No Unencrypted Secret Storage).

**Verification:** Manual security testing and database-backed integration tests verified that protected routes and restricted operations reject unauthorized requests independently of frontend navigation. Direct requests to administrative and reviewer endpoints were tested using accounts without the required permissions. Live deployment testing confirmed that an authenticated User accessing `/admin/users` received a 404 response, while direct access to `/api/admin/users` received a 403 response. Both denied requests generated application-log events. Deployment verification also confirmed that the decryption key was not retained in container environments or found in application image history. These results demonstrate that the tested security controls do not depend on concealing endpoint locations or credential-storage mechanisms. Comprehensive client-side sensitive-data exposure testing remains subject to final security verification.

### 9. Keep Security Simple

The principle of keeping security simple emphasizes minimizing unnecessary complexity in security mechanisms to reduce implementation errors, configuration mistakes, and maintenance difficulties. For our incident-reporting application, this principle is addressed through a modular Next.js architecture and consistent security controls for authentication, authorization, and input validation. Rather than duplicating security logic throughout the application, reusable server-side functions enforce role permissions, validate incoming requests, and protect restricted operations.

Shared authentication and authorization guards, Zod validation schemas, centralized configuration limits, standardized error handling, and reusable audit logging functions provide consistent security behavior across application components. The application also uses Prisma for database operations and a shared transactional audit mechanism to maintain consistency between business operations and their corresponding audit records. The modular monolithic architecture avoids unnecessary distributed services and authentication mechanisms that could introduce additional complexity and security risks. These design decisions make security controls easier to understand, test, and maintain while preserving the protections required by the application.

**Related Security Requirements:** SR-1 (Authentication), SR-4 (Role-Based Access Control), SR-5 (Server-Side Authorization), SR-7 (Input Validation).

**Verification:** Implementation reviews, database-backed integration tests, and manual security testing verified the behavior of shared security mechanisms across authentication, account management, incident management, and administrative operations. Testing confirmed that permitted operations function correctly while unauthorized requests and invalid inputs are rejected. Shared transactional audit behavior was verified through successful operations and simulated audit-write failures. TypeScript, ESLint, and all 125 database-backed integration tests passed during the latest local verification of the integrated application. Comprehensive endpoint coverage remains subject to final security verification.

**Supporting Evidence:** `src/lib/auth/guard.ts`, `src/lib/auth/page.ts`, `src/lib/request.ts`, `src/lib/http.ts`, `src/lib/audit.ts`, `tests/db/audit.test.ts`, `tests/db/incidents.test.ts`, `tests/db/admin-settings.test.ts`, `docs/design.md`, `docs/sdl.md`; PRs #38, #51, #53, #54, and #59.

### 10. Fix Security Issues Correctly

The principle of fixing security issues correctly emphasizes identifying and addressing the underlying causes of vulnerabilities rather than applying temporary or isolated solutions. For our incident-reporting application, this principle is addressed through security testing, code review, and systematic remediation of identified weaknesses. When security issues are identified, corrective changes address the underlying implementation or design deficiency rather than relying solely on frontend restrictions or changes to error messages.

During implementation and integration verification, several security weaknesses were identified and addressed. Incident-detail authorization was corrected to enforce the summary-only access policy for Users at the backend. Malformed incident and category identifiers were addressed through server-side path validation rather than merely suppressing database errors. Incident-list pagination was implemented with bounded database queries and strict parameter validation to reduce excessive resource consumption. Temporary-password reuse was addressed through atomic credential consumption and concurrent first-login protection. Additionally, inconsistent responses for missing and closed incident identifiers were corrected to prevent unauthorized disclosure of incident existence.

Security improvements also included consistent authorization-denial logging and standardized HTTP error and security-header behavior. These changes demonstrate an approach focused on correcting underlying security weaknesses, maintaining consistency across related application components, and reducing the likelihood of recurring vulnerabilities.

**Related Security Requirements:** SR-4 (Role-Based Access Control), SR-5 (Server-Side Authorization), SR-7 (Input Validation), SR-8 (Parameterized Queries), SR-16 (Sensitive Data Exposure, Security Misconfiguration, and Insufficient Logging/Monitoring). Supporting criteria: AC-2–AC-4 (Security Validation, SAST/DAST/Manual Testing, and Lifecycle/AI Documentation). SR-16 addresses these specific security risks rather than establishing a general remediation process.

**Verification:** Security corrections were reviewed through the team's pull-request workflow and evaluated through automated integration testing, static analysis, and targeted manual verification. Database-backed tests verified authorization restrictions, invalid-input rejection, concurrent incident status-update integrity, and transactional rollback behavior. Following integration of the latest changes, all 125 database-backed integration tests passed, along with TypeScript and ESLint checks. Security-related implementation changes, AI assistance, and human validation are documented in the AI usage report and supporting SDL records. Broader DAST, fuzzing, and final remediation verification remain subject to the project's final security review.
