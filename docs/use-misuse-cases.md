# Use and Misuse Cases

Team #13

This is the verification plan for the secure incident-reporting application. Use cases exercise the intended workflows for users, reviewers, administrators, and operators. Misuse cases define the behavior to verify when a security control is challenged. All cases are planned and awaiting execution evidence. [Assignment and acceptance criteria](../ASSIGNMENT.md#9-acceptance-criteria) · [Entry points and design decisions](threat-model.md#14-entry-point-inventory) · [STRIDE threats](stride.md#threats)

## Test setup and evidence

Use an isolated test deployment with HTTPS and a disposable database. Seed two synthetic users, a reviewer, two administrators, and incidents owned by different users across all three statuses. Include active and inactive categories. An operator prepares any temporary-password, session-expiry, concurrency, or service-failure fixtures. Reset mutable fixtures between independent cases and use synthetic data throughout (ASSUMP-2).

For cases involving a write, compare persisted state before and after the action, including the relevant audit records. Successful audited actions should record actor user ID, UTC timestamp, action, and target ID. Rejected requests must leave the protected state unchanged and must not create a success audit event. Failed authentication and authorization belong in sanitized application logs. Record case ID, build or commit, environment, fixture, expected and actual results, pass/fail/blocked, and evidence location. Redact passwords, session tokens, database credentials, and report descriptions from retained evidence. [Security testing report](security-testing.md)

## Misuse cases

The scenarios below specify defensive assertions and evidence for controlled verification. STRIDE IDs retain the original threat ratings in the [STRIDE analysis](stride.md#threats).

| ID | Misuse scenario | Expected defense and evidence | Traceability |
|---|---|---|---|
| MC-01 | Repeated failed privileged sign-ins or account enumeration | Use bounded synthetic login fixtures. Verify per-IP and per-account limits at the configured thresholds, temporary lockout and recovery, equivalent public failure status/message for existing and unknown usernames, and comparable timing across samples. Confirm sanitized application logs record failures. | T-01 to T-04, EP-02 · FR-4, SR-9, SR-16 · V6.1.1, V6.3.1 |
| MC-02 | Invalidated, expired, or unrecognized session is presented | Through session fixtures, check logout, reset, deactivation, idle expiry, and absolute expiry. Protected APIs return 401 for invalid sessions. Verify a sixth session evicts the oldest and initial sign-in issues a new token. | T-05, T-08, T-10 to T-12, EP-02, EP-05, EP-15, EP-17 · FR-5, SR-1, SR-3 · D-5, V7.4.1, V7.4.5 |
| MC-03 | Untrusted origin requests a protected write | Exercise the origin policy at the handler boundary with missing, untrusted, and trusted origin fixtures. Verify the first two are refused even with an otherwise authorized session, and the valid same-origin JSON control succeeds. Check the cookie policy over HTTPS. | T-09, C-4 · SR-3, SR-5 · V3.5.1, V3.5.3 |
| MC-04 | Temporary-password session or unauthorized password change | A session requiring a password change can reach logout and the password flow, while protected business functions are denied. Verify expired temporary credentials, an incorrect current password, and weak or common replacement passwords fail without changing credentials. Check that temporary credentials are excluded from logs. | T-13 to T-16, C-11, EP-06, EP-13, EP-17 · SR-2, SR-4, SR-5, SR-9 · V6.2.3, V6.4.1 |
| MC-05 | Lower-privilege account or anonymous visitor requests restricted functions | Use a role-by-entry-point matrix for protected pages and APIs. Verify anonymous API requests fail with 401 and wrong-role requests fail with 403 where the denial is role-based. Protected pages disclose no protected content. Include user and reviewer access to admin functions and admin requests for reviewer-only status or classification changes. Verify authorization executes in handlers even when middleware is absent in the test harness. | T-19, T-26, T-43, C-1, C-2 · SR-1, SR-4, SR-5 · V8.2.1, V8.3.1 |
| MC-06 | Account attempts to change its own role or set protected fields | Verify all roles are barred from self-role changes, including administrators using the role UI or API. Use schema fixtures with unexpected fields to verify incident, profile, and password operations reject protected account attributes. Confirm own-account deactivation is denied and competing changes cannot remove the last active admin. | T-17, T-18, T-27, EP-06, EP-07, EP-14 to EP-16 · SR-6, SR-7, NFR-5 · V15.3.3, V2.3.4 |
| MC-07 | Someone requests incident data outside their scope | With two users and closed fixtures, check that the personal list remains scoped to its owner and a reviewer cannot see closed records. For an otherwise eligible role requesting a forbidden detail record, verify the same 404 as a missing record. Compare response fields against role allowlists. | T-24, T-25, T-28, EP-08, EP-09, EP-19 · SR-4, SR-5, SR-16 · V8.2.2, V15.3.1 |
| MC-08 | Invalid or competing incident updates | Verify skipped and reversed transitions are rejected, only one of two competing updates from the same expected status succeeds, and only that transition is audited. Check that missing and inactive categories cannot be newly assigned. | T-26, T-27, T-31, EP-10, EP-21 · FR-8, FR-11, SR-7, NFR-5 · V2.3.1, V2.3.4 |
| MC-09 | Malformed settings or stored text is interpreted as markup | Test settings bounds and unknown fields, including a fixture with invalid persisted settings to verify safe defaults. Use inert markup-shaped strings to inspect rendering of report titles, descriptions, comments, category names, usernames, and the public status message. Verify text is escaped, CSP is present, and authenticated responses use `no-store`. | T-21 to T-23, T-29, T-30, EP-07, EP-09, EP-11, EP-20, EP-22 · SR-7, SR-16 · V3.2.2, V14.3.2 |
| MC-10 | Untrusted input alters query behavior or leaks errors | Review query construction and confirm bound parameters or ORM calls for all input paths. With ordinary punctuation in literal text and invalid typed filters in validation fixtures, verify unchanged result scope and rejection of invalid values. Inject a controlled service failure at a test seam. Verify a generic client error, sanitized diagnostic detail in application logs, and recovery on a subsequent valid request. | T-38, T-55, C-3, C-5, C-6 · SR-7 to SR-9, SR-12, SR-13, NFR-2, NFR-6 · V1.2.4, V16.5.1 |
| MC-11 | Audit history is altered or a key action commits without evidence | Inspect the route inventory for absence of audit mutation routes. Check effective database permissions and audit trigger configuration for append-only behavior. At a test seam, force audit insertion to fail and confirm the paired business write rolls back. Verify the audit view is admin-only. | T-33 to T-35, EP-18, C-8 · FR-11, FR-12, SR-9 to SR-11 · V2.3.3, V16.4.2 |
| MC-12 | An external client reaches PostgreSQL or obtains a database secret | Inspect deployment configuration for an unpublished PostgreSQL port and verify that a connectivity check from outside the private application network fails. Confirm that the expected application-to-database connection succeeds. Inspect repository and image scan results for plaintext credentials or key material and verify dotenvx uses an encrypted configuration with its key supplied at runtime. | T-52, T-53, NH-1, NH-3, D-4 · SR-14, SR-16 · V13.2.1, V13.3.1 |
| MC-13 | Vulnerable dependency or forged client metadata weakens a control | Review the locked Next.js and React versions against dependency scan findings. Verify the proxy trust configuration and use handler fixtures to confirm untrusted forwarding metadata cannot change the rate-limit identity. | T-44, T-50 · SR-16, AC-3 · V15.2.1, V15.3.4 |

## Demo sequence

1. Use synthetic user and reviewer accounts to submit, triage, comment on, and close a report. Show the associated audit history from an administrator session (UC-04, UC-05, UC-09).
2. Show rejected administrator sign-in with invalid credentials and a signed-in user being denied access to an administrator function. Include the authorized administrator view as a positive control (MC-01, MC-05).
3. Show that the database is unreachable from outside the private application network while the application continues to serve an authorized workflow (MC-12).
